The problem

Load testing usually goes wrong in three places.

Scripts nobody reads

A k6 file lives on one laptop. Few people on the team can say what it does or whether it still matches the product.

Numbers nobody explains

p95, p99, iterations. The output is a wall of metrics, and a run can look fine while every request fails.

One wrong target

A mistyped URL can send real traffic at a server that is not yours, and take it down.

How it works

From the API you have to a verdict, in four steps.

  1. 01

    Bring what you have.

    Import an OpenAPI spec, a Postman collection (v2.0/2.1), a cURL command or a HAR file. Imported endpoints land in a catalog you pick from instead of retyping.

  2. 02

    Draw the test.

    Requests, extracted variables, conditions, loops, pauses and assertions on a canvas. Ballast writes a readable k6 script from the graph. Prefer code? Write the scenario in k6 directly.

  3. 03

    Prove the target.

    Serve a challenge file on your server. Until it's verified, Ballast sends it no load.

  4. 04

    Run it, read the verdict.

    Pick smoke, load, stress, spike or soak. Watch the output live, then read each threshold — p95, p99, error rate — as Met or Breached.

Features

What Ballast does today.

A canvas that writes k6.

Draw the test; Ballast generates a real k6 script you can read. The same graph always produces the same bytes, so a change to the test is a change you can review.

A script written by hand stays code: it doesn't turn back into a graph.

Imports that leave your secrets behind.

OpenAPI, Postman, cURL, HAR. Tokens, passwords and cookies in the file are never copied: they become secrets you type again.

Load profiles and thresholds.

Smoke, load, stress, spike, soak. Set thresholds on p95, p99 or error rate; Ballast reads the k6 summary and marks each one Met or Breached.

Live output and run history.

The run's output streams to your browser and resumes exactly where it was after a reconnect. Every run keeps its verdict and what was executed — scenario version and profile — frozen on the run.

Projects, roles, audit.

Organizations, projects, roles from viewer to admin, invitations. One project per client. The audit log records who ran what against which target — refusals included.

Environments and secrets.

Secrets are encrypted at rest and never returned by the API. Authorization headers, cookies and secret values are masked in logs. A target only accepts load inside its allowed time windows.

Safety

You can only load what you've proved is yours.

Verified targets.

No load reaches an environment whose ownership hasn't been proved with a challenge file. A refused run is refused with a 403 and written to the audit log.

A caged generator.

The k6 container has no network route of its own. A proxy, filtered per run, lets it reach that run's target — and nothing else.

Honest measurements.

One run at a time per environment, so two runs never measure each other's load. Bytes are measured on the wire for every run.

Hard limits.

200 virtual users and 1 hour per run, constants in the code — not a setting.

Stop everything.

Cancel a run, or cut all load for your organization at once.

Isolation between customers.

PostgreSQL Row-Level Security on every table.

CI

Your pipeline can start a test. It gets no more rights than a person.

CI tokens.

A project token (blt_…) lets a pipeline start a load test with nobody signed in — with the same guardrails as a person: verified target, hard caps, time windows, isolation between customers. One project, two permissions, always an expiry date. Only its SHA-256 hash is stored, and the secret is shown once. The run and the audit log name the token, never a person. A token can only cancel what it started.

Signed webhook.

For any other tool — a deploy script, for example — a signed webhook starts a run. One secret per project, shown once. Each request carries an HMAC-SHA256 signature over the timestamp, a delivery ID and the body; a replayed delivery is ignored.

Self-host

Run it on your own machines, for free.

make selfhost starts the database, migrations, API, web app and a worker in containers. You need Docker, openssl, and your own GitHub or Google OAuth app.

Shell
git clone https://github.com/myballast/ballast.git
cd ballast
make selfhost

Ballast is Fair Source, under the FSL-1.1-ALv2 licence. Use it, change it and redistribute it for anything except a competing commercial service — a company can self-host it for free to test its own applications. Every release becomes Apache 2.0 two years after it ships.

One limit, on purpose: a self-hosted instance only loads targets reachable from the internet. Private, loopback and link-local addresses are refused.

FAQ

Questions people ask first.

Do I need to know k6?

No. Draw the scenario on a canvas or import a file you already have. If you know k6, you can write the scenario in k6 directly.

Only 200 virtual users?

Yes — 200 VUs and one hour per run, in the code. Ballast is built for realistic multi-step API scenarios: log in, extract a token, loop, assert. If you need tens of thousands of concurrent users, other tools are built for that.

Why not just k6 on the command line?

k6 alone works well, and Ballast runs k6. Ballast adds the canvas, imports, verified targets, a caged generator, threshold verdicts, live output, and projects with roles. The scripts stay readable k6.

Can I test any URL?

No, on purpose. Only targets whose ownership you've proved with a challenge file.

Can I test an internal service?

Not today, hosted or self-hosted: a target must be reachable from the internet, and private addresses are refused with no setting to allow them. A runner installed in your network is planned, not available.

What happens to my secrets?

On import, tokens, passwords and cookies are never copied; they become secrets you type again. Secrets are encrypted at rest, the API never returns their value, and they're masked in logs.

Is it open source?

It's Fair Source (FSL-1.1-ALv2): the code is public, and a company can self-host it for free to test its own applications. Only a competing commercial service is excluded, and each release becomes Apache 2.0 after two years.

Does it plug into CI?

Yes, through the API: a project token starts a test with nobody signed in, under the same guardrails as a person, and the audit log names the token. Other tools can use a signed webhook. The CLI, GitHub Action and GitLab template are coming soon — not released yet.

How much does it cost?

Free during the beta. A paid hosted plan will come; self-hosting stays free. No price or date yet.

Can I compare two runs?

Not yet — it's planned. Today every run keeps its own Met / Breached verdict, and a project lists its runs.

It's built by one person. What if it stops?

True, I build it alone. The code is public, you can self-host it, each release becomes Apache 2.0 after two years, and your scenarios are k6.

gRPC, WebSocket, several regions?

HTTP(S) only, from one place. Neither is planned.
